== About this revision

This document describes the architecture of Bitcoin Core: what the major components
are, how they communicate, which threads run what, and where in the tree to look.
It is written to answer the questions you actually have when you first open the
repository — how does the node find peers, what happens when a block arrives, which
thread is my breakpoint sitting on, and why are there seven executables.

All references are pinned to commit
{repo}[`e34b8d5a7dcd45e4faa3bb5fdeae64bf049037f6`] (25 July 2026), which is
`master` at version `31.99.0` — i.e. v32 development, with v31.1 as the most recent
release. Line-number anchors are stable because they point at that commit, not at
`master`.

[source,bash]
----
git clone https://github.com/bitcoin/bitcoin.git
cd bitcoin
git checkout -b arch_text e34b8d5a7dcd45e4faa3bb5fdeae64bf049037f6
----

Bitcoin Core is built with CMake. The build options that matter for reading the
architecture are in the top-level
{repo}/CMakeLists.txt#L103[`CMakeLists.txt`]: `BUILD_DAEMON`, `BUILD_GUI`,
`BUILD_CLI`, `ENABLE_WALLET`, `ENABLE_IPC`, `BUILD_KERNEL_LIB`, and
`BUILD_UTIL_CHAINSTATE`. Which executables exist depends on which of these are on.

== Nodes, wallets, and what Bitcoin Core actually is

To participate in the network without trusting anyone, you need a node: software
that downloads the block chain, independently enforces the consensus rules, and
validates and relays transactions. If you delegate that job to someone else's node,
you inherit their view of the chain and leak your transaction interests to them.

A wallet is a different thing. It manages private keys, derives addresses, tracks
which outputs you can spend, and produces signatures. The protocol has no concept of
accounts; a wallet is bookkeeping over a set of keys and the UTXOs they control.

These two concerns are logically separate even though they have historically shipped
in one binary. Keeping them distinct in your head is most of the work of
understanding the codebase — and, as of the multiprocess work described below, they
are increasingly separate at the process level too.

Bitcoin Core bundles a node, a wallet, a Qt GUI, and a command-line client.
Wallets are not created automatically; you create them explicitly with
`createwallet`, and only descriptor wallets are supported (legacy BDB wallets were
removed, with {repo}/src/wallet/migrate.cpp[`src/wallet/migrate.cpp`] retained purely
to migrate old files).

== Executables

=== The monolithic binaries

`bitcoind`:: {repo}/src/bitcoind.cpp[`src/bitcoind.cpp`]. The node daemon. Starts
the P2P node, the validation engine, the indexes, the JSON-RPC server, the
(unauthenticated, limited) {repo}/doc/REST-interface.md[REST interface], and
optionally the wallet. `main()` calls
{repo}/src/bitcoind.cpp#L169[`AppInit(...)`], which in turn calls
{repo}/src/init.cpp#L1452[`AppInitMain(...)`] — the function where nearly every
subsystem and thread is brought up.

`bitcoin-qt`:: {repo}/src/qt/main.cpp[`src/qt/main.cpp`]. Everything `bitcoind`
does, plus the Qt GUI, in one process. Only one of `bitcoind` and `bitcoin-qt` can
use a given data directory at a time.

`bitcoin-cli`:: {repo}/src/bitcoin-cli.cpp[`src/bitcoin-cli.cpp`]. Speaks
{repo}/doc/JSON-RPC-interface.md[JSON-RPC] over HTTP to a running node and prints
the result.

`bitcoin-tx`:: {repo}/src/bitcoin-tx.cpp[`src/bitcoin-tx.cpp`]. Offline creation and
editing of hex-encoded raw transactions.

`bitcoin-util`:: {repo}/src/bitcoin-util.cpp[`src/bitcoin-util.cpp`]. Offline
utility for things like block header grinding. Did not exist when the original
document was written.

`bitcoin-wallet`:: {repo}/src/bitcoin-wallet.cpp[`src/bitcoin-wallet.cpp`]. Offline
wallet file tool: create, salvage, dump, and migrate wallets without a node.

=== The `bitcoin` wrapper

New since the original text: a single front-end binary,
{repo}/src/bitcoin.cpp[`src/bitcoin.cpp`], which dispatches to the others. Its
{repo}/src/bitcoin.cpp#L23[usage string] is the clearest one-screen summary of the
whole executable layout:

[source,cpp]
----
Options:
  -m, --multiprocess     Run multiprocess binaries bitcoin-node, bitcoin-gui.
  -M, --monolithic       Run monolithic binaries bitcoind, bitcoin-qt. (Default behavior)

Commands:
  gui [ARGS]     Start GUI, equivalent to running 'bitcoin-qt [ARGS]' or 'bitcoin-gui [ARGS]'.
  node [ARGS]    Start node, equivalent to running 'bitcoind [ARGS]' or 'bitcoin-node [ARGS]'.
  rpc [ARGS]     Call RPC method, equivalent to running 'bitcoin-cli -named [ARGS]'.
  wallet [ARGS]  Call wallet command, equivalent to running 'bitcoin-wallet [ARGS]'.
  tx [ARGS]      Manipulate hex-encoded transactions, equivalent to running 'bitcoin-tx [ARGS]'.
----

So `bitcoin node -signet` and `bitcoind -signet` are the same thing, and
`bitcoin -m node` selects the multiprocess build of the node instead.

=== Multiprocess binaries and IPC

The original document described process separation as a *proposal*. It has largely
landed. {repo}/CMakeLists.txt#L122[`ENABLE_IPC`] now defaults to `ON` on
non-Windows platforms, which builds two additional executables:

`bitcoin-node`:: {repo}/src/init/bitcoin-node.cpp[`src/init/bitcoin-node.cpp`]. The
node, indexes, and JSON-RPC server, exposing an IPC socket.

`bitcoin-gui`:: {repo}/src/qt/CMakeLists.txt#L279[`src/qt/CMakeLists.txt`]. A
standalone GUI that connects to a `bitcoin-node` over IPC rather than embedding it.

The node listens on `<datadir>/node.sock`; wallet and GUI processes connect to it.
The mechanism is Cap'n Proto over a Unix socket, with
https://github.com/chaincodelabs/libmultiprocess[libmultiprocess] vendored as a git
subtree under {tree}/src/ipc/libmultiprocess[`src/ipc/libmultiprocess`]. The moving
parts:

* {tree}/src/interfaces[`src/interfaces/`] — abstract C++ classes
  (`interfaces::Node`, `Chain`, `WalletLoader`, `Mining`, `Init`, `Ipc`) with pure
  virtual methods. Code in `src/node/`, `src/wallet/`, and `src/qt/` calls *only*
  through these, which is what makes the same call work in-process or across a
  socket.
* {tree}/src/ipc/capnp[`src/ipc/capnp/`] — `.capnp` schemas and the code generator
  that turns those interfaces into serialisable requests.
* {tree}/src/init[`src/init/`] — one small translation unit per executable
  (`bitcoind.cpp`, `bitcoin-node.cpp`, `bitcoin-qt.cpp`, `bitcoin-gui.cpp`,
  `bitcoin-wallet.cpp`, `basic.cpp`) selecting whether interfaces are satisfied
  locally or over IPC.

The full design rationale is in
{repo}/doc/design/multiprocess.md[`doc/design/multiprocess.md`].

=== The kernel library

{tree}/src/kernel[`src/kernel/`] contains `libbitcoin_kernel`: the validation engine
factored out from the rest of the node, with a C API in
{repo}/src/kernel/bitcoinkernel.h[`kernel/bitcoinkernel.h`] and a C++ RAII wrapper in
{repo}/src/kernel/bitcoinkernel_wrapper.h[`bitcoinkernel_wrapper.h`]. It is still
experimental — gated behind `BUILD_KERNEL_LIB` — and the demonstration consumer is
{repo}/src/bitcoin-chainstate.cpp[`bitcoin-chainstate`], which validates blocks with
no P2P, wallet, or RPC involved. This is the most useful entry point in the tree if
you want to read validation in isolation.

Note which things live in `kernel/` and which do not:
chain parameters ({repo}/src/kernel/chainparams.cpp[`kernel/chainparams.cpp`], which
is where the DNS seeds moved to), mempool options and limits, the
`kernel::Notifications` interface, and `cs_main` itself
({repo}/src/kernel/cs_main.h[`kernel/cs_main.h`]).

=== Library layout

{repo}/doc/design/libraries.md[`doc/design/libraries.md`] is authoritative and has a
Mermaid dependency graph. The convention worth memorising: each library has a
directory and a namespace — `libbitcoin_node` in `src/node/` as `node::`,
`libbitcoin_wallet` in `src/wallet/` as `wallet::`, `libbitcoin_ipc` in `src/ipc/`
as `ipc::`, `libbitcoin_util` in `src/util/` as `util::`, `libbitcoin_consensus` in
`src/consensus/` as `Consensus::`. Every library except `libbitcoin_kernel` has a
deliberately unstable API.

== Protocol — P2P

=== Message types

{repo}/src/protocol.h#L60[`namespace NetMsgType`] in
{repo}/src/protocol.h[`src/protocol.h`] declares every wire message type, each with a
comment describing its purpose. These are now `inline constexpr const char*` rather
than `extern const char*`:

[source,cpp]
----
namespace NetMsgType {
/**
 * The version message provides information about the transmitting node to the
 * receiving node at the beginning of a connection.
 */
inline constexpr const char* VERSION{"version"};
// ...
inline constexpr const char* ADDRV2{"addrv2"};
inline constexpr const char* SENDADDRV2{"sendaddrv2"};
// ...
} // namespace NetMsgType
----

Anything added here must also be added to
{repo}/src/protocol.h#L274[`ALL_NET_MESSAGE_TYPES`]. Relative to the 2021 list, the
notable additions are `ADDRV2`/`SENDADDRV2` (BIP155), `WTXIDRELAY` (BIP339), the
compact block filter messages (`GETCFILTERS`, `CFILTER`, `GETCFHEADERS`,
`CFHEADERS`, `GETCFCHECKPT`, `CFCHECKPT`), `SENDTXRCNCL` for Erlay transaction
reconciliation, and — most recently —
{repo}/src/protocol.h#L313[`FEATURE`], a generic post-`version` feature-negotiation
message with `MAX_FEATUREID_LENGTH` and `MAX_FEATUREDATA_LENGTH` bounds and a
currently-empty `NetMsgFeature` namespace awaiting its first user.

Not visible in `protocol.h` at all: the BIP324 v2 encrypted transport, implemented in
{repo}/src/bip324.cpp[`src/bip324.cpp`] and
{repo}/src/net.cpp[`net.cpp`]'s `V2Transport`, which encrypts and obfuscates the
message framing itself.

=== Finding peers

On a first run the node has no peers, so it queries hardcoded DNS seeds, each of
which returns addresses of recently-live nodes. These live in
{repo}/src/kernel/chainparams.cpp#L168[`src/kernel/chainparams.cpp`] — moved from
`src/chainparams.cpp` since the original text:

[source,cpp]
----
vSeeds.emplace_back("dnsseed.bluematt.me.");             // Matt Corallo, only supports x9
vSeeds.emplace_back("seed.bitcoin.jonasschnelli.ch.");   // Jonas Schnelli
vSeeds.emplace_back("seed.btc.petertodd.net.");          // Peter Todd
vSeeds.emplace_back("seed.bitcoin.sprovoost.nl.");       // Sjors Provoost
vSeeds.emplace_back("dnsseed.emzy.de.");                 // Stephan Oeste
vSeeds.emplace_back("seed.bitcoin.wiz.biz.");            // Jason Maurice
vSeeds.emplace_back("seed.mainnet.achownodes.xyz.");     // Ava Chow
----

The list has turned over: `seed.bitcoin.sipa.be`, `dnsseed.bitcoin.dashjr.org`, and
`seed.bitcoinstats.com` are gone from mainnet, and `achownodes.xyz` is new. Testnet3,
testnet4, and signet have their own seed lists further down the same file. Learned
addresses are managed by {repo}/src/addrman.h[`AddrMan`] and persisted to
`peers.dat`; the seed query is a bootstrap of last resort, skipped entirely if
`-dnsseed=0` or if enough addresses are already known.

Peers can also be pinned manually with `-addnode=<addr>` or `-connect=<ip>`, and
`-seednode` provides a one-shot address source.

=== Connection limits

Defined in {repo}/src/net.h#L69[`src/net.h`]:

[source,cpp]
----
static const int MAX_OUTBOUND_FULL_RELAY_CONNECTIONS = 8;
static const int MAX_ADDNODE_CONNECTIONS = 8;
static const int MAX_BLOCK_RELAY_ONLY_CONNECTIONS = 2;
static const int MAX_FEELER_CONNECTIONS = 1;
static constexpr size_t MAX_PRIVATE_BROADCAST_CONNECTIONS{64};
static const unsigned int DEFAULT_MAX_PEER_CONNECTIONS{200};
----

{repo}/src/net.h#L1118[`CConnman::Init(...)`] derives the rest: 8 full-relay + 2
block-relay-only + 1 feeler = 11 automatic outbound connections, with the remainder
of the 200-connection budget available for inbound. `MAX_PRIVATE_BROADCAST_CONNECTIONS`
is new and belongs to the private broadcast feature described below.

== Concurrency model

The node does many things at once: syncing headers and blocks, validating them,
accepting and relaying transactions, serving RPC, responding to GUI events. It is
heavily multithreaded, and the single most useful fact for a newcomer is that
*almost all `net_processing` and validation logic runs on one thread* — `b-msghand`.
Parallelism is concentrated in a few specific places (script checks, prevout
fetching, RPC workers), not spread across the codebase.

Thread names are set by `util::ThreadRename` and carry a `b-` prefix in the OS view,
which is what you see in `gdb`'s `info threads` or `top -H`. Most threads are started
directly or indirectly from {repo}/src/init.cpp#L1452[`AppInitMain(...)`]; the
network threads are started from
{repo}/src/net.cpp#L3557[`CConnman::Start(...)`], which `AppInitMain` calls.

=== `util::TraceThread`

Every long-lived thread is wrapped in
{repo}/src/util/thread.h[`util::TraceThread`], which renames the thread, logs its
start and exit, and makes sure an escaping exception is logged rather than silently
terminating the process. It moved out of the old `util/system.h` into
{repo}/src/util/thread.cpp#L15[`src/util/thread.cpp`], and the Boost dependency is
gone:

[source,cpp]
----
void util::TraceThread(std::string_view thread_name, std::function<void()> thread_func)
{
    util::ThreadRename(std::string{thread_name});
    try {
        LogInfo("%s thread start", thread_name);
        thread_func();
        LogInfo("%s thread exit", thread_name);
    } catch (const std::exception& e) {
        PrintExceptionContinue(&e, thread_name);
        throw;
    } catch (...) {
        PrintExceptionContinue(nullptr, thread_name);
        throw;
    }
}
----

Call sites pass it as the callable to `std::thread`, with a lambda for the body:

[source,cpp]
----
threadSocketHandler = std::thread(&util::TraceThread, "net", [this] { ThreadSocketHandler(); });
----

The name "trace thread" suggests run-once semantics, and the wrapper does call its
function exactly once — but the functions themselves generally contain a loop that
runs until interrupted, so a single call keeps the thread alive for the node's
lifetime. `ThreadSocketHandler` is the canonical example:

[source,cpp]
----
void CConnman::ThreadSocketHandler()
{
    while (!m_interrupt_net->interrupted()) {
        DisconnectNodes();
        NotifyNumConnectionsChanged();
        SocketHandler();
    }
}
----

Interruption is now expressed through
{repo}/src/util/signalinterrupt.h[`util::SignalInterrupt`] (`m_interrupt_net`)
rather than the old `CThreadInterrupt`/`interruptNet` pair, which matters because the
same object is used to plumb shutdown requests down from signal handlers.

=== `util::ThreadPool`

New infrastructure since the original text:
{repo}/src/util/threadpool.h#L47[`util::ThreadPool`], a general worker pool with
`Start`, `Stop`, `Interrupt`, and a task queue. Workers are themselves wrapped in
`TraceThread` and named `<pool>.NN`:

[source,cpp]
----
for (int i = 0; i < num_workers; i++) {
    m_workers.emplace_back(&util::TraceThread, strprintf("%s.%02d", m_name, i), [this] { WorkerThread(); });
}
----

Two pools exist today: the HTTP worker pool
({repo}/src/httpserver.cpp#L77[`g_threadpool_http`]) and the prevout-fetching pool
owned by `CoinsViewOverlay`.

=== Script verification

Script execution itself is
{repo}/src/script/interpreter.cpp[`VerifyScript(...)`] in
`src/script/interpreter.cpp`. Everything that needs to check an input's script goes
through {repo}/src/validation.cpp#L2073[`CheckInputScripts(...)`], reached from
three directions:

. A transaction arrives from a peer. `net_processing` calls
  {repo}/src/validation.cpp#L4471[`ChainstateManager::ProcessTransaction(...)`]
  (or {repo}/src/validation.h#L291[`ProcessNewPackage(...)`] for a package), which
  runs the `MemPoolAccept` pipeline. Note that the old peer-facing
  `AcceptToMemoryPool` free function is no longer the entry point;
  {repo}/src/validation.h#L277[it still exists] but `ProcessTransaction` is what
  `net_processing` and the RPC layer call.
. The node broadcasts its own transaction:
  {repo}/src/node/transaction.cpp#L32[`BroadcastTransaction(...)`], same pipeline.
. A block arrives: `ChainstateManager::ProcessNewBlock` →
  `ActivateBestChain` → {repo}/src/validation.cpp#L2307[`Chainstate::ConnectBlock(...)`].

`CheckInputScripts` builds one
{repo}/src/validation.h#L341[`CScriptCheck`] per input — a closure capturing the
spent output, the spending transaction, the input index, the verification flags, the
precomputed transaction data, and a pointer to the signature cache:

[source,cpp]
----
class CScriptCheck
{
private:
    CTxOut m_tx_out;
    const CTransaction *ptxTo;
    unsigned int nIn;
    script_verify_flags m_flags;
    bool cacheStore;
    PrecomputedTransactionData *txdata;
    SignatureCache* m_signature_cache;
    // ...
    std::optional<std::pair<ScriptError, std::string>> operator()();
};
----

Three changes here are worth flagging against the older text. `operator()` returns
`std::optional<std::pair<ScriptError, std::string>>` rather than `bool`, so a failing
check carries its own error out rather than stashing it in a member. The class is
move-only with `static_assert`s on nothrow move, because it is stored in vectors on
a hot path. And the signature cache is no longer a global — it is reached through
`ValidationCache`, owned by `ChainstateManager`.

The `pvChecks` parameter decides whether verification happens now or later:

[source,cpp]
----
CScriptCheck check(txdata.m_spent_outputs[i], tx, validation_cache.m_signature_cache,
                   i, flags, cacheSigStore, &txdata);
if (pvChecks) {
    pvChecks->emplace_back(std::move(check));
} else if (auto result = check(); result.has_value()) {
    // ... verification failed, fill in state
}
----

Only `ConnectBlock` passes a non-null `pvChecks`, because only a block has enough
inputs to be worth parallelising. It does so through
{repo}/src/checkqueue.h#L208[`CCheckQueueControl`]:

[source,cpp]
----
std::vector<PrecomputedTransactionData> txsdata(block.vtx.size());
std::optional<CCheckQueueControl<CScriptCheck>> control;
if (auto& queue = m_chainman.GetCheckQueue(); queue.HasThreads() && fScriptChecks) control.emplace(queue);
// ... per-transaction:
if (tx_ok) control->Add(std::move(vChecks));
// ... then:
auto parallel_result = control->Complete();
----

The global `g_parallel_script_checks` and `StartScriptCheckWorkerThreads` from the
original text are both gone. The queue is now a member of `ChainstateManager`:

[source,cpp]
----
//! A queue for script verifications that have to be performed by worker threads.
CCheckQueue<CScriptCheck> m_script_check_queue;
----

constructed with a batch size of 128 and a clamped thread count, and reached via
{repo}/src/validation.h#L1380[`GetCheckQueue()`]. Worker threads are spawned in
`CCheckQueue`'s constructor and joined in its destructor, so their lifetime is tied
to `ChainstateManager`'s rather than to an explicit start call from `init.cpp`.
`HasThreads()` replaces the old boolean flag as the "can we parallelise" test.

The thread count is computed in
{repo}/src/node/chainstatemanager_args.cpp#L54[`node/chainstatemanager_args.cpp`],
with the same `-par` semantics as before — `0` means autodetect, `-n` means leave
`n` cores free — and the ceiling is still
{repo}/src/validation.h#L90[`MAX_SCRIPTCHECK_THREADS{15}`]:

[source,cpp]
----
int script_threads = args.GetIntArg("-par", DEFAULT_SCRIPTCHECK_THREADS);
if (script_threads <= 0) {
    // -par=0 means autodetect (number of cores - 1 script threads)
    // -par=-n means "leave n cores free" (number of cores - n - 1 script threads)
    script_threads += GetNumCores();
}
// Subtract 1 because the main thread counts towards the par threads.
opts.worker_threads_num = script_threads - 1;
----

The master thread joins the worker pool as an Nth worker while waiting, which is why
one is subtracted.

=== Parallel prevout fetching

A second axis of parallelism inside block validation, with no counterpart in the
original document. Before scripts can be checked, `ConnectBlock` must fetch every
spent output from the coins database — an I/O-bound scatter of LevelDB reads that
parallelises well. {repo}/src/validation.cpp#L1863[`CoinsViews::InitCache`] hands a
`ThreadPool` to a {repo}/src/coins.h#L653[`CoinsViewOverlay`] for exactly this:

[source,cpp]
----
auto thread_pool{std::make_shared<ThreadPool>("prevout")};
if (prevoutfetch_threads > 0) {
    thread_pool->Start(prevoutfetch_threads);
    LogInfo("Block input prevout fetching uses %d additional threads", prevoutfetch_threads);
}
m_connect_block_view = std::make_unique<CoinsViewOverlay>(&*m_cacheview, std::move(thread_pool));
----

Controlled by `-prevoutfetchthreads`, bounded by
{repo}/src/validation.h#L93[`MAX_PREVOUTFETCH_THREADS{16}`], and disabled with `0`.

=== Loading blocks — the `initload` thread

The original `ThreadImport`/`loadblk` thread has been generalised. A single
background thread, {repo}/src/node/context.h#L101[`node.background_init_thread`],
performs everything that is part of startup but must not block the node from coming
up: external block import (`-loadblock`), reindex, initial chain activation, index
background sync, and mempool load from disk.

[source,cpp]
----
node.background_init_thread = std::thread(&util::TraceThread, "initload",
        [=, &chainman, &args, &kernel_notifications, &node] {
    ScheduleBatchPriority();
    // Import blocks and ActivateBestChain()
    ImportBlocks(chainman, vImportFiles);
    // ...
    WITH_LOCK(::cs_main, chainman.UpdateIBDStatus());
    // ...
    if (!StartIndexBackgroundSync(node)) { /* fatal */ }
    if (auto* pool{chainman.ActiveChainstate().GetMempool()}) {
        LoadMempool(*pool, ShouldPersistMempool(args) ? MempoolPath(args) : fs::path{},
                    chainman.ActiveChainstate(), {});
        pool->SetLoadTried(!chainman.m_interrupt);
    }
});
----

`ImportBlocks` now lives in
{repo}/src/node/blockstorage.cpp#L1276[`node/blockstorage.cpp`], and the thread
handle lives in `NodeContext` rather than being a `ChainstateManager` member or a
global. `ScheduleBatchPriority()` deprioritises the thread so a slow reindex does
not starve the rest of the node.

=== Servicing RPC calls

This subsystem has been rewritten wholesale. **libevent is gone**; Bitcoin Core now
implements HTTP itself on top of {repo}/src/util/sock.h[`util::Sock`]. There are
still comments in {repo}/src/httpserver.cpp[`httpserver.cpp`] referencing libevent
behaviour, but only as documentation of the semantics being reproduced.

{repo}/src/init.cpp#L784[`AppInitServers(...)`] calls `InitHTTPServer()` to bind, then
{repo}/src/httpserver.cpp#L1258[`StartHTTPServer()`]:

[source,cpp]
----
void StartHTTPServer()
{
    auto rpcThreads{std::max(gArgs.GetArg<int>("-rpcthreads", DEFAULT_HTTP_THREADS), 1)};
    LogInfo("Starting HTTP server with %d worker threads", rpcThreads);
    g_threadpool_http.Start(rpcThreads);
    g_http_server->StartSocketsThreads();
}
----

One acceptor thread (`b-http`, running
{repo}/src/httpserver.cpp#L958[`HTTPServer::ThreadSocketHandler`]) reads and parses
requests; a {repo}/src/util/threadpool.h#L47[`ThreadPool`] of workers
(`b-http.00`, `b-http.01`, …) executes them off the event loop.
{repo}/src/httpserver.h#L35[`DEFAULT_HTTP_THREADS`] is now **16**, up from 4, and
`-rpcworkqueue` still bounds queue depth (requests beyond it are rejected with a
warning rather than queued indefinitely).

Shutdown is a three-stage dance worth knowing about if you are chasing lifetime bugs
in this area: {repo}/src/httpserver.cpp#L1266[`InterruptHTTPServer`] swaps the
request handler for `RejectRequest` *before* interrupting the pool, then
`StopHTTPServer` stops the pool, stops accepting, and waits up to 30 seconds for
clients to disconnect gracefully — with an explicit ordering comment that
`StopAccepting()` must precede `DisconnectAllClients()`, because a connection
accepted after the count reads zero would otherwise survive into the destructor.

=== Loading peer addresses from DNS seeds

{repo}/src/net.h#L1774[`threadDNSAddressSeed`] runs
{repo}/src/net.cpp#L2290[`CConnman::ThreadDNSAddressSeed()`]. It is created in
`CConnman::Start` only if seeding is enabled:

[source,cpp]
----
if (!gArgs.GetBoolArg("-dnsseed", DEFAULT_DNSSEED))
    LogInfo("DNS seeding disabled\n");
else
    threadDNSAddressSeed = std::thread(&util::TraceThread, "dnsseed", [this] { ThreadDNSAddressSeed(); });
----

The thread does not blindly query on every start: it waits, checks how many
addresses `AddrMan` already holds and how many outbound peers are connected, and
only falls through to DNS if the node genuinely needs addresses.

=== Sending and receiving — the socket handler

{repo}/src/net.h#L1775[`threadSocketHandler`] runs the loop shown earlier:
`DisconnectNodes()`, `NotifyNumConnectionsChanged()`, `SocketHandler()`.

`DisconnectNodes()` drops everything if `-setnetworkactive` has turned the network
off, and otherwise reaps peers flagged `fDisconnect` and frees nodes whose refcount
has hit zero. `NotifyNumConnectionsChanged()` pokes the UI. `SocketHandler()` does
the actual `select`/`poll`, accepts inbound connections, reads bytes into each
peer's receive buffer, and writes queued bytes out. It deliberately does no
application-level interpretation — deserialising and acting on messages is
`b-msghand`'s job.

=== Initiating outbound connections

{repo}/src/net.h#L1777[`threadOpenConnections`] runs
{repo}/src/net.cpp#L2592[`ThreadOpenConnections(...)`] and is responsible for
choosing peers, honouring network-group diversity via
{repo}/src/netgroup.h[`NetGroupManager`] (and ASMap, if configured), and opening
full-relay, block-relay-only, and feeler connections up to the limits above. Whether
it starts at all depends on configuration:

[source,cpp]
----
if (connOptions.m_use_addrman_outgoing || !connOptions.m_specified_outgoing.empty()) {
    threadOpenConnections = std::thread(
        &util::TraceThread, "opencon",
        [this, connect = connOptions.m_specified_outgoing, seed_nodes = std::move(seed_nodes)] {
            ThreadOpenConnections(connect, seed_nodes);
        });
}
----

`-connect=0` disables automatic outbound connections entirely, in which case the
thread is never created; `-connect=<ip>` restricts outbound connections to exactly
what was specified. Supplying both `-connect` and letting AddrMan pick is rejected
at startup with an error dialog.

=== Opening added connections

{repo}/src/net.h#L1776[`threadOpenAddedConnections`] runs
{repo}/src/net.cpp#L3052[`ThreadOpenAddedConnections()`], which polls
`GetAddedNodeInfo()` for peers supplied via `-addnode` or the `addnode` RPC and
calls `OpenNetworkConnection(...)` for any that are not currently connected. These
are accounted separately from automatic connections, up to
`MAX_ADDNODE_CONNECTIONS`. (The original document mislabelled this thread's member
variable as `threadMessageHandler`; they are distinct.)

=== I2P

{repo}/src/net.h#L1779[`threadI2PAcceptIncoming`] runs
{repo}/src/net.cpp#L3257[`ThreadI2PAcceptIncoming()`], started only when an I2P SAM
session was configured with `-i2psam`. It accepts inbound I2P connections through
the SAM proxy. See {repo}/doc/i2p.md[`doc/i2p.md`]; the CJDNS and Tor equivalents
are documented alongside it.

=== Private broadcast

Entirely new: {repo}/src/net.h#L1780[`threadPrivateBroadcast`] runs
{repo}/src/net.cpp#L3302[`ThreadPrivateBroadcast()`], gated on
`-privatebroadcast`. The idea is to reduce the privacy cost of originating a
transaction: instead of announcing your own transaction to your regular peers —
which links it to your node — the node opens short-lived, dedicated connections
(over Tor, in the intended deployment) and hands the transaction to peers that know
nothing else about you.

{repo}/src/private_broadcast.h[`PrivateBroadcast`] tracks which transactions still
need sending, which peer each was handed to, and whether it has been seen coming
back from the network. Its own header documents the timing policy:
`INITIAL_STALE_DURATION{5min}` before a never-delivered transaction is retried, and
`STALE_DURATION{1min}` after broadcast without hearing it echo back.

=== Processing messages — `net` → `net_processing`

{repo}/src/net.h#L1778[`threadMessageHandler`] runs
{repo}/src/net.cpp#L3216[`CConnman::ThreadMessageHandler()`]. This is the thread you
will spend most of your debugging life on:

[source,cpp]
----
void CConnman::ThreadMessageHandler()
{
    LOCK(NetEventsInterface::g_msgproc_mutex);

    while (!flagInterruptMsgProc)
    {
        bool fMoreWork = false;
        {
            // Randomize the order in which we process messages from/to our peers.
            const NodesSnapshot snap{*this, /*shuffle=*/true};

            for (CNode* pnode : snap.Nodes()) {
                if (pnode->fDisconnect) continue;
                bool fMoreNodeWork{m_msgproc->ProcessMessages(*pnode, flagInterruptMsgProc)};
                fMoreWork |= (fMoreNodeWork && !pnode->fPauseSend);
                if (flagInterruptMsgProc) return;
                m_msgproc->SendMessages(*pnode);
                if (flagInterruptMsgProc) return;
            }
        }
        WAIT_LOCK(mutexMsgProc, lock);
        if (!fMoreWork) {
            condMsgProc.wait_until(lock, std::chrono::steady_clock::now() + std::chrono::milliseconds(100),
                                   [this]() EXCLUSIVE_LOCKS_REQUIRED(mutexMsgProc) { return fMsgProcWake; });
        }
        // ...
    }
}
----

Two details worth internalising. The peer iteration order is deliberately shuffled
on every pass, so an attacker holding several consecutive slots in `m_nodes` cannot
rely on being serviced in a fixed order. And the whole loop holds
`g_msgproc_mutex`, which is the formal statement that message processing is
single-threaded — a lot of `net_processing` state carries
`EXCLUSIVE_LOCKS_REQUIRED(g_msgproc_mutex)` annotations that are satisfied only
because of this.

`m_msgproc` is the {repo}/src/net_processing.h#L89[`PeerManager`], which is now an
abstract interface with a `PeerManagerImpl` in
{repo}/src/net_processing.cpp[`net_processing.cpp`]. Transaction download
scheduling — orphan handling, request timeouts, per-peer announcement tracking —
has been factored out into {repo}/src/node/txdownloadman.h[`node/txdownloadman.h`]
with {repo}/src/node/txorphanage.h[`txorphanage`] and
{repo}/src/txrequest.h[`txrequest`] beneath it, rather than living directly in
`net_processing` as it once did.

=== The scheduler

{repo}/src/scheduler.h#L38[`CScheduler`] is a single-threaded task queue with
support for scheduling work at a time, after a delay, or on a repeating interval.
Its loop is {repo}/src/scheduler.cpp#L23[`CScheduler::serviceQueue()`], started
early in `AppInitMain`:

[source,cpp]
----
scheduler.m_service_thread = std::thread(util::TraceThread, "scheduler", [&] { scheduler.serviceQueue(); });
----

It runs periodic maintenance — `DumpAddresses()` on `DUMP_PEERS_INTERVAL`, the ASMap
health check every 24h, wallet flushing, fee estimate dumping — and, importantly, it
is the execution context for asynchronous validation callbacks, described next.

== Notification mechanisms

There are two distinct notification systems in the tree, and confusing them is a
common early mistake.

=== `ValidationSignals` and `CValidationInterface`

Many components need to react to validation events: the wallet when a relevant
transaction confirms, `net_processing` when the tip advances, indexes when a block
connects, ZMQ subscribers on essentially everything. Rather than having validation
call each of them directly, Bitcoin Core uses a publish/subscribe arrangement with
an asynchronous queue in the middle, so that a slow subscriber cannot block
validation.

{repo}/src/validationinterface.h#L49[`CValidationInterface`] is the subscriber
interface. Every method is `virtual` with an empty default body, so a subscriber
implements only the events it cares about:

[source,cpp]
----
class CValidationInterface {
protected:
    virtual void UpdatedBlockTip(const CBlockIndex *pindexNew, const CBlockIndex *pindexFork, bool fInitialDownload) {}
    virtual void ActiveTipChange(const CBlockIndex& new_tip, bool is_ibd) {};
    virtual void TransactionAddedToMempool(const NewMempoolTransactionInfo& tx, uint64_t mempool_sequence) {}
    virtual void TransactionRemovedFromMempool(const CTransactionRef& tx, MemPoolRemovalReason reason, uint64_t mempool_sequence) {}
    virtual void MempoolTransactionsRemovedForBlock(const std::vector<RemovedMempoolTransactionInfo>& txs_removed_for_block, unsigned int nBlockHeight) {}
    virtual void BlockConnected(const kernel::ChainstateRole& role, const std::shared_ptr<const CBlock>& block, const CBlockIndex* pindex) {}
    virtual void BlockDisconnected(const std::shared_ptr<const CBlock> &block, const CBlockIndex* pindex) {}
    virtual void ChainStateFlushed(const kernel::ChainstateRole& role, const CBlockLocator& locator) {}
    virtual void BlockChecked(const std::shared_ptr<const CBlock>&, const BlockValidationState&) {}
    virtual void NewPoWValidBlock(const CBlockIndex *pindex, const std::shared_ptr<const CBlock>& block) {};
    friend class ValidationSignals;
};
----

Three signatures changed in ways that tell you something about the architecture.
`TransactionAddedToMempool` now receives a `NewMempoolTransactionInfo` rather than a
bare `CTransactionRef`, so subscribers get fee and size information without
re-querying the mempool under a lock. `BlockConnected` and `ChainStateFlushed` take a
`kernel::ChainstateRole`, because with assumeutxo there can be two chainstates and a
subscriber usually cares about only one of them. And `ActiveTipChange` and
`MempoolTransactionsRemovedForBlock` are new events.

The publisher side is where the biggest change lies. The old global
`CMainSignals g_signals` is gone, replaced by
{repo}/src/validationinterface.h#L161[`ValidationSignals`], an object owned by
{repo}/src/node/context.h#L97[`NodeContext`] and constructed with an explicit task
runner:

[source,cpp]
----
node.validation_signals = std::make_unique<ValidationSignals>(std::make_unique<SerialTaskRunner>(scheduler));
----

The `SerialTaskRunner` dispatches callbacks on the scheduler thread, serially, so
subscribers see events in order and never on the validation thread.
{repo}/src/util/task_runner.h[`ImmediateTaskRunner`] is the synchronous alternative,
used by the kernel library and in tests where a scheduler would be overkill. Passing
the runner in as a constructor argument — rather than baking a global scheduler
dependency into the signal machinery — is what makes `libbitcoin_kernel` usable
without a node.

Registration is unchanged in spirit but is now a method call rather than a free
function: `RegisterValidationInterface` for raw pointers whose lifetime the caller
manages, and `RegisterSharedValidationInterface` for `shared_ptr` subscribers where
the pointer must survive until the last queued notification has been delivered.

Current subscribers:

* {repo}/src/net_processing.h#L89[`PeerManager`]
* {repo}/src/index/base.h#L54[`BaseIndex`] (txindex, block filter index, coinstats index, txospender index)
* {repo}/src/policy/fees/block_policy_estimator.h#L147[`CBlockPolicyEstimator`]
* {repo}/src/zmq/zmqnotificationinterface.h#L21[`CZMQNotificationInterface`]
* {repo}/src/node/interfaces.cpp#L466[`NotificationsProxy`] (the bridge to `interfaces::Chain` consumers, i.e. the wallet and GUI)
* {repo}/src/node/miner.cpp#L366[`SubmitBlockStateCatcher`] and {repo}/src/rpc/mining.cpp#L1069[`submitblock_StateCatcher`]
* {repo}/src/kernel/bitcoinkernel.cpp#L335[`KernelValidationInterface`]

`CBlockPolicyEstimator` as a subscriber is new and reflects fee estimation having
moved into {tree}/src/policy/fees[`src/policy/fees/`] as a proper subsystem.

=== `kernel::Notifications`

The second mechanism, with no equivalent in the original document.
{repo}/src/kernel/notifications_interface.h#L35[`kernel::Notifications`] is a
*synchronous* interface for things the validation engine must tell its host
immediately, and which cannot go through a queue:

[source,cpp]
----
class Notifications
{
public:
    [[nodiscard]] virtual InterruptResult blockTip(SynchronizationState state, const CBlockIndex& index, double verification_progress) { return {}; }
    virtual void headerTip(SynchronizationState state, int64_t height, int64_t timestamp, bool presync) {}
    virtual void progress(const bilingual_str& title, int progress_percent, bool resume_possible) {}
    virtual void warningSet(Warning id, const bilingual_str& message) {}
    virtual void warningUnset(Warning id) {}
    virtual void flushError(const bilingual_str& message) {}
    virtual void fatalError(const bilingual_str& message) {}
};
----

The node's implementation is
{repo}/src/node/kernel_notifications.h#L43[`node::KernelNotifications`]. Note that
`blockTip` returns an `InterruptResult` — this is the path by which validation
learns that shutdown has been requested and unwinds. Progress reporting, startup
warnings, and fatal errors also travel here rather than through `ValidationSignals`,
precisely because they must not be deferred.

The division of labour: `ValidationSignals` is for consumers that react to chain
events asynchronously; `kernel::Notifications` is for the embedder that needs to
know *now*.

== Chainstates and assumeutxo

The original document's `CChainState` is now
{repo}/src/validation.h#L553[`Chainstate`], and the interesting structure is above
it. {repo}/src/validation.h#L944[`ChainstateManager`] owns the block index
(`BlockManager`), the script check queue, the validation caches, and — the key point —
potentially *two* `Chainstate` objects.

This is the assumeutxo mechanism. Given a serialised UTXO set snapshot,
{repo}/src/validation.h#L1113[`ChainstateManager::ActivateSnapshot(...)`] creates a
second chainstate initialised from that snapshot, allowing the node to sync forward
from a recent height and become usable within minutes, while a background chainstate
independently validates the chain from genesis up to the snapshot's base block. When
the background validation catches up and the UTXO set hashes agree, the snapshot
chainstate is confirmed and the background one is discarded; if they disagree,
that is a fatal error.

The consequence for reading code is the `kernel::ChainstateRole` parameter that
appears throughout the notification interfaces and in
{repo}/src/validation.h#L1369[`ActivateBestChains()`]: subscribers must distinguish
"a block connected in the chainstate the user is actually using" from "a block
connected during background validation". Indexes and the wallet care about one;
statistics-gathering code may care about both.

See {repo}/doc/design/assumeutxo.md[`doc/design/assumeutxo.md`] for the mechanism
and {repo}/doc/assumeutxo.md[`doc/assumeutxo.md`] for operator-facing usage.

== The mempool and `TxGraph`

The mempool has been substantially rearchitected since the original text.
{repo}/src/txmempool.h[`CTxMemPool`] still holds the `boost::multi_index` container
of entries, but the relationships between unconfirmed transactions have been
extracted into {repo}/src/txgraph.h[`TxGraph`]:

[source,cpp]
----
std::unique_ptr<TxGraph> m_txgraph GUARDED_BY(cs);
mutable std::unique_ptr<TxGraph::BlockBuilder> m_builder GUARDED_BY(cs);
----

`TxGraph` is deliberately Bitcoin-agnostic: it knows about nodes, dependencies,
fees, and sizes, and it answers questions about clusters and optimal linearisations.
The Bitcoin-specific policy lives in `CTxMemPool` on top of it. Many `CTxMemPool`
methods are now thin wrappers — `GetDescendantCount`, for instance, is a
`m_txgraph->GetDescendants(...)` call.

Policy limits moved accordingly. Ancestor and descendant count limits are no longer
the mempool's admission criterion; *cluster* limits are, defined in
{repo}/src/policy/policy.h#L72[`src/policy/policy.h`] and
{repo}/src/kernel/mempool_limits.h#L20[`kernel/mempool_limits.h`]:

[source,cpp]
----
static constexpr unsigned int DEFAULT_CLUSTER_LIMIT{64};
static constexpr unsigned int DEFAULT_CLUSTER_SIZE_LIMIT_KVB{101};
----

A cluster is the set of unconfirmed transactions connected to each other directly or
indirectly. `-limitclustercount` bounds it. `-limitancestorcount` and
`-limitdescendantcount` still exist but are marked deprecated in
{repo}/src/init.cpp#L682[`init.cpp`] and are now used only by the wallet for coin
selection — the mempool itself ignores them.

The practical significance is that mining and eviction can now reason about
transaction packages optimally rather than heuristically:
`TxGraph::BlockBuilder` produces a linearisation for block template construction,
and explicit work budgets in {repo}/src/txmempool.h#L52[`txmempool.h`] —
`ACCEPTABLE_COST{75'000}` and `POST_CHANGE_COST` (five times that) — cap how much
linearisation effort the graph is asked to spend after each mempool change.

====
Companion to the updated `1.0_bitcoin_core_architecture.asciidoc`, and an
independently rewritten successor to Chaincode Labs'
https://github.com/chaincodelabs/bitcoin-core-onboarding/blob/main/1.1_regions.asciidoc[`1.1_regions.asciidoc`],
which was pinned to commit `4b5659c6b1` (mid-2021) and whose repository was archived
in December 2023.

Where 1.0 covers processes, threads, and control flow, this document covers the
*static* decomposition: which directory owns which responsibility, which classes
matter in each, and how neighbouring regions talk to each other.

The original's region map still broadly holds, but several of its load-bearing
claims are now wrong rather than merely dated. The peer misbehaviour *scoring*
system has been deleted outright, so the points table in the 2021 text describes
machinery that no longer exists. `script/standard.{h,cpp}` has been split apart.
The mempool's multi-index has gone from five indices to three. `CChainState` is
`Chainstate`. `SaveBlockToDisk` is gone. <<appendix-diff,Appendix A>> lists the
deltas.
====

== About this revision

All references are pinned to {repo}[`e34b8d5a7dcd45e4faa3bb5fdeae64bf049037f6`]
(25 July 2026), `master` at version `31.99.0` — v32 development, with v31.1 the
most recent release.

[source,bash]
----
git clone https://github.com/bitcoin/bitcoin.git
cd bitcoin
git checkout -b regions_text e34b8d5a7dcd45e4faa3bb5fdeae64bf049037f6

A note on the word "region". It is a reading aid, not a project convention. The
tree's own vocabulary is *libraries* — see
{repo}/doc/design/libraries.md[`doc/design/libraries.md`] — and library boundaries
are enforced by the build, whereas regions are just clusters of related files. The
two mostly coincide, but not always: `validation.cpp` is split across
`libbitcoin_kernel` and `libbitcoin_node`, and `src/node/` contains files belonging
to both. Where a distinction matters it is flagged below.

== The region map

[cols="3,2,4",options="header"]
|===
| Files | Layer | Responsibility

| <<net,`net.{h,cpp}`>>
| Network
| Sockets, connection management, message framing and encryption

| <<net_processing,`net_processing.{h,cpp}`>>
| Network processing
| Interprets P2P messages and drives validation on their behalf

| <<validation,`validation.{h,cpp}`>>
| Validation
| Chainstate, block and transaction acceptance, flushing

| <<blockstorage,`node/blockstorage.{h,cpp}`>>
| Block storage
| `blk*.dat`/`rev*.dat` files and the block index database

| <<txmempool,`txmempool.{h,cpp}`, `txgraph.{h,cpp}`>>
| Mempool
| Unconfirmed transactions and the relationships between them

| <<coins,`coins.{h,cpp}`, `txdb.{h,cpp}`>>
| Coins
| The UTXO cache hierarchy and the chainstate database

| <<dbwrapper,`dbwrapper.{h,cpp}`, `index/`>>
| Database and indexes
| LevelDB wrapper; optional txindex, filter, coinstats, txospender indexes

| <<script,`script/`, `addresstype.{h,cpp}`>>
| Script
| Opcodes, interpreter, solver, signing, descriptors, miniscript

| <<consensus,`consensus/`>>
| Consensus
| Rules that must never change without a fork

| <<policy,`policy/`>>
| Policy
| Local relay and mempool rules; fee estimation

| <<kernel,`kernel/`>>
| Kernel
| The validation engine as a reusable library

| <<node,`node/`>>
| Node
| Node-level glue that is not consensus: mining, warnings, tx download, persistence

| <<interfaces,`interfaces/`, `ipc/`>>
| Interface / IPC
| Abstract boundaries between node, wallet, and GUI — in-process or across a socket

| <<rpc,`rpc/`>>
| RPC server
| Dispatch table, request handling, JSON conversion

| <<qt,`qt/`>>
| GUI
| Qt interface

| <<wallet,`wallet/`>>
| Wallet
| Keys, descriptors, coin selection, spending

| <<mining,`node/miner.{h,cpp}`, `interfaces/mining.h`>>
| Mining
| Block template assembly

| <<common,`common/`, `util/`>>
| Common and util
| Shared helpers below everything else
|===

The rough dependency direction is bottom-up: `util` → `crypto`/`consensus` →
`kernel` → `node` → `net_processing`/`rpc`/`wallet` → `qt`. Arrows that point the
other way are usually mediated by `interfaces/`.

[[net]]
== `net.{h,cpp}`

The bottom of the stack. It knows about sockets, bytes, and peers; it knows nothing
about what a block or a transaction means.

=== Wiring

The network comes up when {repo}/src/init.cpp#L1452[`AppInitMain(...)`] calls
`node.connman->Start(*node.scheduler, connOptions)`. Two things get passed in.

`connOptions` is a {repo}/src/net.h#L1088[`CConnman::Options`], holding every
user-configurable network parameter, with defaults from `net.h`.

The `node` is a {repo}/src/node/context.h#L59[`NodeContext`] — the struct that
replaced the old global `g_conman` and friends. It has grown considerably since the
2021 text and is now the best single-screen inventory of what a running node
consists of:

[source,cpp]
----
struct NodeContext {
    std::unique_ptr<kernel::Context> kernel;
    std::unique_ptr<ECC_Context> ecc_context;
    interfaces::Init* init{nullptr};
    std::function<bool()> shutdown_request;
    util::SignalInterrupt* shutdown_signal{nullptr};
    std::unique_ptr<AddrMan> addrman;
    std::unique_ptr<CConnman> connman;
    std::unique_ptr<CTxMemPool> mempool;
    std::unique_ptr<const NetGroupManager> netgroupman;
    std::unique_ptr<CBlockPolicyEstimator> fee_estimator;
    std::unique_ptr<PeerManager> peerman;
    std::unique_ptr<ChainstateManager> chainman;
    std::unique_ptr<BanMan> banman;
    std::vector<BaseIndex*> indexes;
    std::unique_ptr<interfaces::Chain> chain;
    std::vector<std::unique_ptr<interfaces::ChainClient>> chain_clients;
    std::unique_ptr<interfaces::Mining> mining;
    std::unique_ptr<CScheduler> scheduler;
    std::unique_ptr<KernelNotifications> notifications;
    std::unique_ptr<ValidationSignals> validation_signals;
    std::unique_ptr<node::Warnings> warnings;
    std::thread background_init_thread;
    // ...
};
----

Note `kernel`, `init`, `mining`, `notifications`, `validation_signals`, and
`warnings` — all absent in 2021, and each of them a marker of a subsystem that has
since been extracted from a global or from `validation.cpp`. The header's own
comment is worth taking seriously: this struct is meant to be a collection of
references with no member functions, so that including it does not drag in
half the tree.

=== Address storage

`CConnman::Start` loads addresses from `peers.dat` into
{repo}/src/addrman.h[`AddrMan`], recreating the file if it is unreadable. Separately
it reads `anchors.dat`:

[source,cpp]
----
m_anchors = ReadAnchors(gArgs.GetDataDirNet() / ANCHORS_DATABASE_FILENAME);
if (m_anchors.size() > MAX_BLOCK_RELAY_ONLY_ANCHORS) {
    m_anchors.resize(MAX_BLOCK_RELAY_ONLY_ANCHORS);
}
----

The two files serve different threat models. `peers.dat` is the general address
database used for outbound-full-relay connections; `anchors.dat` records up to
{repo}/src/net.cpp#L58[`MAX_BLOCK_RELAY_ONLY_ANCHORS`] (2) block-relay-only peers
from the last clean shutdown, reconnected on startup so that an adversary cannot
cheaply replace your entire peer set across a restart. The former mitigates topology
inference (the *TxProbe* line of work), the latter eclipse attacks.
`AddrMan` is persisted every
{repo}/src/net.cpp#L64[`DUMP_PEERS_INTERVAL`] (15 minutes) via a scheduler task.

=== Transports

New since the original text: message framing is now behind an abstraction.
{repo}/src/net.h#L263[`Transport`] is the interface;
{repo}/src/net.h#L376[`V1Transport`] is the classic plaintext framing with the
4-byte magic, 12-byte command, length and checksum;
{repo}/src/net.h#L458[`V2Transport`] implements BIP324's encrypted transport, with
the handshake and rekeying logic in {repo}/src/bip324.cpp[`src/bip324.cpp`]. A peer
connection can negotiate v2 and fall back to v1. Everything above `net.cpp` sees
deserialised messages either way.

The threads owned by this region (`net`, `dnsseed`, `addcon`, `opencon`, `msghand`,
`i2paccept`, `privbcast`) are covered in the architecture document.

[[net_processing]]
== `net_processing.{h,cpp}`

The adapter between the network and validation. {repo}/src/net_processing.h#L89[`PeerManager`]
is the abstract interface; {repo}/src/net_processing.cpp#L565[`PeerManagerImpl`] is
the implementation, and it inherits three interfaces:

* {repo}/src/validationinterface.h#L49[`CValidationInterface`] — so it hears about
  new blocks and tip changes (see the architecture document).
* {repo}/src/net.h#L1040[`NetEventsInterface`] — peer lifecycle and the
  `ProcessMessages`/`SendMessages` entry points called from `ThreadMessageHandler`.
* `PeerManager` itself — the higher-level API used by RPC and init.

`NetEventsInterface` also owns {repo}/src/net.h#L1044[`g_msgproc_mutex`], the static
mutex held for the whole duration of the message-handling loop. Much of this
region's state is annotated `EXCLUSIVE_LOCKS_REQUIRED(g_msgproc_mutex)` and is
therefore safe only because message processing is single-threaded.

`ProcessMessages` (plural) is the per-peer pump: drain pending `getdata` requests,
do orphan work, then hand a single message to `ProcessMessage` (singular), which is
the large dispatch on `msg_type` that decodes each message and calls into
validation.

=== Transaction download

The orphan-handling and request-scheduling logic that used to sit directly in this
file has been extracted into
{repo}/src/node/txdownloadman.h[`node::TxDownloadManager`], held as
{repo}/src/net_processing.cpp#L864[`m_txdownloadman`]:

[source,cpp]
----
node::TxDownloadManager m_txdownloadman GUARDED_BY(m_tx_download_mutex);
----

It sits on top of {repo}/src/node/txorphanage.h[`txorphanage`] (transactions whose
parents are missing) and {repo}/src/txrequest.h[`txrequest`] (which peer to ask for
what, and when to time out), and it is what decides whether a rejected transaction
should be retried, cached as invalid, or assembled into a package for
`ProcessNewPackage`. If you are tracing why a transaction was or was not requested,
this is the region to read, not `ProcessMessage`.

=== Misbehaviour — the scoring system is gone

This is the single largest correction to the 2021 document. There is no longer a
misbehaviour *score*, no `DISCOURAGEMENT_THRESHOLD`, and no table of point values.
{repo}/src/net_processing.cpp#L2011[`Misbehaving`] now takes a peer and a message,
and any call to it means immediate discouragement:

[source,cpp]
----
void PeerManagerImpl::Misbehaving(Peer& peer, const std::string& message)
{
    LOCK(peer.m_misbehavior_mutex);

    const std::string message_prefixed = message.empty() ? "" : (": " + message);
    peer.m_should_discourage = true;
    LogDebug(BCLog::NET, "Misbehaving: peer=%d%s\n", peer.m_id, message_prefixed);
    TRACEPOINT(net, misbehaving_connection, peer.m_id, message.c_str());
}
----

The rationale was that graduated scoring gave a false sense of precision: in
practice every misbehaviour that mattered was worth 100 points, and the 20-point
categories were either unreachable or triggered by honest peers. Removing the score
also removed a subtle attack surface, since an adversary could previously stay just
under the threshold indefinitely.

What remains is a much shorter list of call sites — out-of-bounds `getblocktxn`
indices, headers with invalid proof of work, non-continuous header sequences,
failed compact-block reconstruction, and the consensus-invalid cases routed through
{repo}/src/net_processing.cpp#L2024[`MaybePunishNodeForBlock`] and
`MaybePunishNodeForTx`. Discouraged peers are still recorded in
{repo}/src/banman.h[`BanMan::m_discouraged`]. Note also that `Misbehaving` logs at
`LogDebug(BCLog::NET, ...)` rather than the old `LogPrint`, and now emits a USDT
tracepoint, which is the more convenient hook if you want to watch this live.

[[validation]]
== `validation.{h,cpp}`

Still the largest region, still the result of decomposing the historical
`main.{h,cpp}`, and still being broken up. Its job is verifying received data and
maintaining the in-memory chainstate.

=== `Chainstate` and `ChainstateManager`

`CChainState` is now {repo}/src/validation.h#L553[`Chainstate`], and
{repo}/src/validation.h#L944[`ChainstateManager`] sits above it. `ChainstateManager`
owns the block index (`BlockManager`), the script check queue, the validation
caches, and up to two `Chainstate` objects — the assumeutxo arrangement described in
the architecture document. `ProcessNewBlock` and `ProcessNewBlockHeaders` are
`ChainstateManager` members; `AcceptBlock`, `ActivateBestChain`,
`ActivateBestChainStep`, `ConnectTip`, and `ConnectBlock` are `Chainstate` members.

The chain of calls when a block arrives is unchanged in shape:

....
PeerManagerImpl::ProcessMessage (BLOCK / BLOCKTXN / CMPCTBLOCK)
  └─ ChainstateManager::ProcessNewBlock
       └─ Chainstate::AcceptBlock          → writes the block to disk
            └─ Chainstate::ActivateBestChain
                 └─ Chainstate::ActivateBestChainStep
                      └─ Chainstate::ConnectTip
                           └─ Chainstate::ConnectBlock   → the real work
....

`net_processing` reaches all of this through a `ChainstateManager& m_chainman`
member, which is the only coupling between the two regions.

=== Validation caches

The globals are gone. {repo}/src/validation.h#L373[`ValidationCache`] bundles what
used to be `g_scriptExecutionCache` and the standalone signature cache:

[source,cpp]
----
class ValidationCache
{
private:
    CSHA256 m_script_execution_cache_hasher;

public:
    CuckooCache::cache<uint256, SignatureCacheHasher> m_script_execution_cache;
    SignatureCache m_signature_cache;
    // ...
};
----

The script execution cache is keyed on the witness hash plus the verification flags,
so a transaction validated on entry to the mempool need not have its scripts
re-executed when it appears in a block under the same flags. The signature cache
sits a level lower, memoising individual signature checks. Both are sized from
`-maxsigcachesize`, now split between the two. `ChainstateManager` owns the
`ValidationCache`, which is what makes the kernel library usable without global
initialisation.

=== Flushing

{repo}/src/validation.h#L742[`Chainstate::FlushStateToDisk`] is called on every
chainstate change and decides, from cache pressure and elapsed time, whether to do a
full flush.
{repo}/src/validation.h#L748[`ForceFlushStateToDisk`] is the shutdown path. Three
distinct writes happen: block and undo files are finalised, the block index database
is written, and the coins cache is flushed to the chainstate database. The details
of the first two have moved out of this file — see the next region.

=== What has moved out

Mempool persistence is no longer here. `DumpMempool` and `LoadMempool` live in
{repo}/src/node/mempool_persist.h#L16[`node/mempool_persist.{h,cpp}`], called from
shutdown and from the `initload` thread respectively. Fee estimation moved to
`policy/fees/`. Block reading and writing moved to `node/blockstorage`. The
long-running effort to reduce this file continues; expect further extraction.

[[blockstorage]]
== `node/blockstorage.{h,cpp}`

Promoted to a region of its own since the 2021 text, where it barely appeared. Its
centre is {repo}/src/node/blockstorage.h#L195[`BlockManager`], which owns the
on-disk block data and the block index.

The old free functions are now members with different names:

[cols="2,2",options="header"]
|===
| 2021 | Now

| `SaveBlockToDisk(...)`
| removed; callers use `BlockManager::WriteBlock` directly

| `WriteBlockToDisk(...)`
| {repo}/src/node/blockstorage.h#L396[`BlockManager::WriteBlock`], returning a `FlatFilePos`

| `ReadBlockFromDisk(...)`
| {repo}/src/node/blockstorage.h#L476[`BlockManager::ReadBlock`]

| `UndoWriteToDisk` / `UndoReadFromDisk`
| {repo}/src/node/blockstorage.h#L385[`WriteBlockUndo`] / {repo}/src/node/blockstorage.h#L480[`ReadBlockUndo`]

| `CBlockTreeDB` in `txdb.h`
| {repo}/src/node/blockstorage.h#L101[`BlockTreeDB`], declared here in the `kernel` namespace
|===

The four kinds of data the node keeps on disk are unchanged, and remain the clearest
mental model of the data directory:

`blocks/blk*.dat`:: Raw blocks in network serialisation, appended sequentially.
Needed for rescans, reorgs, and serving blocks to peers. Capped at
{repo}/src/node/blockstorage.h#L126[`MAX_BLOCKFILE_SIZE`] (128 MiB) per file.

`blocks/rev*.dat`:: Undo data — the reverse patch for each block, letting the node
roll the chainstate backwards during a reorg.

`blocks/index/`:: LevelDB metadata for every known block, including where on disk to
find it.

`chainstate/`:: LevelDB holding the UTXO set.

{repo}/doc/files.md[`doc/files.md`] documents the rest of the data directory.

[[txmempool]]
== `txmempool.{h,cpp}` and `txgraph.{h,cpp}`

The most structurally changed region in the tree.

=== Acceptance

Validation still happens in `validation.cpp` before anything is inserted here. The
{repo}/src/validation.cpp#L444[`MemPoolAccept`] class runs the checks in increasing
order of cost, so that a bad transaction is rejected as cheaply as possible:

* {repo}/src/validation.cpp#L677[`PreChecks`] — policy checks excluding scripts:
  standardness, size, inputs available, feerate, cluster limits.
* {repo}/src/validation.cpp#L680[`ReplacementChecks`] — the RBF rules, factored out
  of `PreChecks` since 2021 and used only in the single-transaction path.
* {repo}/src/validation.cpp#L689[`PolicyScriptChecks`] — scripts under policy flags.
* {repo}/src/validation.cpp#L695[`ConsensusScriptChecks`] — scripts again under
  consensus flags, with the result cached.
* `Finalize` / {repo}/src/validation.cpp#L703[`SubmitPackage`] — insertion,
  removing conflicts first.
* {repo}/src/validation.cpp#L708[`CheckFeeRate`] — minimum feerate enforcement.

The entry points are `AcceptSingleTransaction...` and `AcceptMultipleTransactions...`
variants, the latter being the package path that did not exist in 2021. Externally
this region is reached through
{repo}/src/validation.cpp#L4471[`ChainstateManager::ProcessTransaction`] and
{repo}/src/validation.h#L291[`ProcessNewPackage`], not the old bare
`AcceptToMemoryPool`.

=== The entry

{repo}/src/kernel/mempool_entry.h[`CTxMemPoolEntry`] moved into `kernel/` and lost
its most distinctive members. It is now purely a description of *one* transaction:

[source,cpp]
----
const CTransactionRef tx;
const CAmount nFee;
const int32_t nTxWeight;
const size_t nUsageSize;
const int64_t nTime;
const uint64_t entry_sequence;
const unsigned int entryHeight;
const bool spendsCoinbase;
const int64_t sigOpCost;
mutable CAmount m_modified_fee;
----

The `Parents m_parents` and `Children m_children` sets from the 2021 version are
gone entirely. Relationships between unconfirmed transactions are no longer stored
per-entry.

=== The container, and `TxGraph`

The `boost::multi_index` container survives but has been cut from five indices to
three:

[source,cpp]
----
using indexed_transaction_set = boost::multi_index_container<
    CTxMemPoolEntry,
    boost::multi_index::indexed_by<
        // sorted by txid
        boost::multi_index::hashed_unique<mempoolentry_txid, SaltedTxidHasher>,
        // sorted by wtxid
        boost::multi_index::hashed_unique<
            boost::multi_index::tag<index_by_wtxid>, mempoolentry_wtxid, SaltedWtxidHasher>,
        // sorted by entry time
        boost::multi_index::ordered_non_unique<
            boost::multi_index::tag<entry_time>,
            boost::multi_index::identity<CTxMemPoolEntry>,
            CompareTxMemPoolEntryByEntryTime>
    >
>;
----

The descendant-feerate and ancestor-feerate indices are gone. Everything that used
them — mining selection, eviction ordering, RBF comparison, ancestor and descendant
queries — now goes through {repo}/src/txmempool.h#L259[`m_txgraph`]:

[source,cpp]
----
std::unique_ptr<TxGraph> m_txgraph GUARDED_BY(cs);
mutable std::unique_ptr<TxGraph::BlockBuilder> m_builder GUARDED_BY(cs);
----

{repo}/src/txgraph.h[`TxGraph`] is deliberately Bitcoin-agnostic: it manipulates
nodes, dependencies, fees and sizes, and answers questions about *clusters* — the
connected components of the unconfirmed transaction graph — and their optimal
linearisations. `CTxMemPool` supplies the Bitcoin-specific policy on top. Many
`CTxMemPool` methods are now one-line forwards; `GetDescendantCount`, for example,
is a `m_txgraph->GetDescendants(...)` call.

Two consequences worth knowing:

*Changesets.* {repo}/src/txmempool.h#L644[`CTxMemPool::ChangeSet`] batches a set of
additions and removals so they can be evaluated as a unit before being applied.
{repo}/src/txmempool.h#L698[`CalculateChunksForRBF`] produces the feerate diagrams
that the modern replacement rules compare, which is what makes it possible to reason
about whether a replacement genuinely improves the mempool rather than applying the
older heuristics.

*Limits.* Cluster limits (`-limitclustercount`, default 64) are the admission
criterion. `-limitancestorcount` and `-limitdescendantcount` still exist but are
deprecated to wallet coin-selection use.

{repo}/src/txmempool.h#L776[`CCoinsViewMemPool`] is unchanged in purpose: a view
that answers coin lookups from the UTXO set *and* from unconfirmed mempool outputs,
so a transaction spending an unconfirmed parent can be validated and signed.

[[coins]]
== `coins.{h,cpp}` and `txdb.{h,cpp}`

The layered cache over the UTXO set. The hierarchy has one new member:

* {repo}/src/coins.h#L355[`CCoinsView`] — abstract base.
* {repo}/src/txdb.h#L36[`CCoinsViewDB`] — the `chainstate/` LevelDB, holding every
  unspent output.
* {repo}/src/coins.h#L415[`CCoinsViewBacked`] — a view backed by another view.
* {repo}/src/coins.h#L798[`CCoinsViewErrorCatcher`] — turns database read failures
  into a controlled shutdown rather than an exception in the middle of validation.
* {repo}/src/coins.h#L436[`CCoinsViewCache`] — the in-memory cache, sized by
  `-dbcache`.
* {repo}/src/coins.h#L653[`CoinsViewOverlay`] — **new**: a `CCoinsViewCache`
  subclass carrying a `ThreadPool` for parallel prevout fetching.
* {repo}/src/txmempool.h#L776[`CCoinsViewMemPool`] — adds unconfirmed outputs.

`Chainstate` reaches all of this through
{repo}/src/validation.h#L482[`CoinsViews`], which has gained a fourth member since
2021:

[source,cpp]
----
class CoinsViews {
public:
    CCoinsViewDB m_dbview GUARDED_BY(cs_main);
    CCoinsViewErrorCatcher m_catcherview GUARDED_BY(cs_main);
    std::unique_ptr<CCoinsViewCache> m_cacheview GUARDED_BY(cs_main);

    //! Reused CoinsViewOverlay layered on top of m_cacheview and passed to ConnectBlock().
    //! Reset between calls and flushed only on success, so invalid blocks don't pollute
    //! the underlying cache.
    std::unique_ptr<CoinsViewOverlay> m_connect_block_view GUARDED_BY(cs_main);

    CoinsViews(DBParams db_params, CoinsViewOptions options);
    void InitCache(int32_t prevoutfetch_threads) EXCLUSIVE_LOCKS_REQUIRED(::cs_main);
};
----

`m_connect_block_view` is the interesting one. Block connection now writes into a
scratch overlay that is flushed to `m_cacheview` only if the block turns out to be
valid — so a block that fails late in validation cannot leave partial state in the
main cache. It also carries the prevout-fetch thread pool.

[[dbwrapper]]
== `dbwrapper.{h,cpp}` and `index/`

{repo}/src/dbwrapper.h[`CDBWrapper`] wraps LevelDB: `Read`, `Write`, `Erase`,
`Exists`, `WriteBatch`. Three classes derive from or use it — `CCoinsViewDB` for the
chainstate, `BlockTreeDB` for the block index, and `BaseIndex::DB` for the optional
indexes.

The obfuscation mechanism survives — an 8-byte random key XORed over stored values,
originally added to stop antivirus software from flagging the chainstate — but the
implementation moved into {repo}/src/util/obfuscation.h[`util/obfuscation.h`] as a
proper `Obfuscation` type, held as
{repo}/src/dbwrapper.h#L202[`m_obfuscation`] and persisted under the key
`\0obfuscate_key`.

=== Indexes

{repo}/src/index/base.h#L54[`BaseIndex`] implements `CValidationInterface`, so each
index simply overrides
{repo}/src/index/base.h#L126[`CustomAppend`] and lets the base class handle
block-connected events, background sync, and rewind on reorg. Each index runs its
own sync thread and owns a {repo}/src/index/base.h#L64[`BaseIndex::DB`], a nested
`CDBWrapper` subclass.

There are now four, up from two:

[cols="2,1,3",options="header"]
|===
| Index | Flag | Purpose

| `TxIndex`
| `-txindex`
| Locate any transaction by txid. Required by block explorers.

| `BlockFilterIndex`
| `-blockfilterindex`
| BIP157/158 compact block filters, served to light clients. Compatible with pruning.

| `CoinStatsIndex`
| `-coinstatsindex`
| Precomputed UTXO set statistics, so `gettxoutsetinfo` need not scan.

| `TxoSpenderIndex`
| `-txospenderindex`
| **New**: maps each spent output to the transaction that spent it.
|===

Databases land under `indexes/<name>/`.

[[script]]
== `script/` and `addresstype.{h,cpp}`

=== The split

`script/standard.{h,cpp}` no longer exists. It was divided along a useful seam:

* {repo}/src/addresstype.h[`src/addresstype.{h,cpp}`] — the *destination* types,
  i.e. the things an address can denote.
* {repo}/src/script/solver.h[`script/solver.{h,cpp}`] — `Solver()` and
  `GetScriptForDestination()`, i.e. recognising and constructing script templates.

`CTxDestination` has grown accordingly:

[source,cpp]
----
using CTxDestination = std::variant<CNoDestination, PubKeyDestination, PKHash,
                                    ScriptHash, WitnessV0ScriptHash, WitnessV0KeyHash,
                                    WitnessV1Taproot, PayToAnchor, WitnessUnknown>;
----

`WitnessV1Taproot` (P2TR) and {repo}/src/addresstype.h#L123[`PayToAnchor`] — the
`OP_1 <0x4e73>` pay-to-anchor output type used for fee-bumping presigned
transactions — are both new since 2021.

=== The rest of the region

`script.{h,cpp}`:: Opcodes and `CScript` (a `prevector<28, unsigned char>`, chosen to
keep small scripts inline), plus `CScriptNum` for the 4-byte-operand,
64-bit-result arithmetic semantics.

`interpreter.{h,cpp}`:: `EvalScript` executes opcodes; `VerifyScript` drives a full
input verification. Called from `CheckInputScripts` in validation.

`verify_flags.h`:: **New** — `script_verify_flags` as a distinct type rather than a
bare `unsigned int`, so policy and consensus flag sets cannot be silently
interchanged.

`sigcache.{h,cpp}`:: `CachingTransactionSignatureChecker`, backed by a
`SignatureCache` that is now a member of `ValidationCache` rather than a global. It
short-circuits repeated ECDSA and Schnorr verification.

`sign.{h,cpp}`, `signingprovider.{h,cpp}`:: Transaction signing and the key/script
lookup abstraction the signer uses.

`descriptor.{h,cpp}`:: Output script descriptors — the basis of modern wallets. See
{repo}/doc/descriptors.md[`doc/descriptors.md`].

`miniscript.{h,cpp}`, `parsing.{h,cpp}`:: **New** — Miniscript, a structured
language for spending policies that compiles to Bitcoin Script with analysable
satisfaction costs, plus its shared parsing helpers.

[[consensus]]
== `consensus/`

The rules that cannot change without a fork. The constants in
{repo}/src/consensus/consensus.h[`consensus/consensus.h`] are mostly familiar:

[source,cpp]
----
static const unsigned int MAX_BLOCK_SERIALIZED_SIZE = 4000000;
static const unsigned int MAX_BLOCK_WEIGHT = 4000000;
static const int64_t MAX_BLOCK_SIGOPS_COST = 80000;
static const int COINBASE_MATURITY = 100;
static const int WITNESS_SCALE_FACTOR = 4;
static const size_t MIN_TRANSACTION_WEIGHT = WITNESS_SCALE_FACTOR * 60;
static const size_t MIN_SERIALIZABLE_TRANSACTION_WEIGHT = WITNESS_SCALE_FACTOR * 10;
static constexpr int64_t MAX_TIMEWARP = 600;
----

`MAX_TIMEWARP` is the addition to watch — the bound on how far a block's timestamp
may precede the previous difficulty period's, closing the timewarp attack. Check
`chainparams.cpp` for which networks currently enforce it before assuming anything
about mainnet.

`MAX_MONEY` moved from `amount.h` to
{repo}/src/consensus/amount.h[`consensus/amount.h`].

`tx_check.{h,cpp}` holds context-free transaction checks; `tx_verify.{h,cpp}` holds
the contextual ones (`CheckTxInputs`, sequence locks, sigop counting).
`merkle.{h,cpp}` computes `BlockMerkleRoot` and `BlockWitnessMerkleRoot`.
`validation.h` here defines `TxValidationState` and `BlockValidationState`, whose
result enums are what `MaybePunishNodeForTx`/`MaybePunishNodeForBlock` switch on.

=== Deployments

{repo}/src/consensus/params.h[`consensus/params.h`] now distinguishes two kinds of
rule activation:

[source,cpp]
----
enum BuriedDeployment : int16_t {
    // buried deployments get negative values to avoid overlap with DeploymentPos
    // ...
};
enum DeploymentPos : uint16_t {
    // ...
};
----

*Buried* deployments are historical soft forks whose activation heights are now
hardcoded because they are far behind any reasonable reorg — BIP34, BIP65, BIP66,
CSV, Segwit. They are checked by height comparison, not by version-bit state.
*Versionbits* deployments (`DeploymentPos`) are the BIP9 machinery in
{repo}/src/versionbits.h[`versionbits.{h,cpp}`] and
{repo}/src/deploymentstatus.h[`deploymentstatus.{h,cpp}`], with human-readable names
in `deploymentinfo.cpp`. `BIP16Exception` is gone; P2SH is buried.

Per-network values are set in
{repo}/src/kernel/chainparams.cpp[`kernel/chainparams.cpp`] — note the move into
`kernel/` — for mainnet, testnet3, testnet4, signet, and regtest.

[[policy]]
== `policy/`

Local rules: what this node will relay and accept, as distinct from what is valid.
The region has roughly doubled in size.

`policy.{h,cpp}`:: `IsStandardTx`, `GetVirtualTransactionSize`, dust rules, and the
standardness constants:
+
[source,cpp]
----
static constexpr int32_t MAX_STANDARD_TX_WEIGHT{400000};
static constexpr unsigned int MIN_STANDARD_TX_NONWITNESS_SIZE{65};
static constexpr unsigned int MAX_STANDARD_TX_SIGOPS_COST{MAX_BLOCK_SIGOPS_COST/5};
static constexpr bool DEFAULT_PERMIT_BAREMULTISIG{true};
static constexpr unsigned int DUST_RELAY_TX_FEE{3000};
static constexpr unsigned int DEFAULT_MIN_RELAY_TX_FEE{100};
static const unsigned int MAX_OP_RETURN_RELAY = MAX_STANDARD_TX_WEIGHT / WITNESS_SCALE_FACTOR;
----
+
Two of these are worth flagging as recently changed and locally contentious.
`DEFAULT_MIN_RELAY_TX_FEE` is 100 sat/kvB, an order of magnitude below the
long-standing 1000. And `MAX_OP_RETURN_RELAY` is now effectively the standard
transaction size limit rather than a small fixed number, reflecting the datacarrier
relaxation. Both are *policy*, adjustable per node, and both were the subject of
substantial public disagreement — treat any summary of the reasoning, including
this one, as a starting point rather than a settled account.

`truc_policy.{h,cpp}`:: **New** — topologically restricted until confirmation
("TRUC", version 3 transactions, BIP431). Opting into version 3 buys tighter
topology limits in exchange for reliable fee-bumping, which is what makes
pinning-resistant contracting protocols practical.

`ephemeral_policy.{h,cpp}`:: **New** — ephemeral dust: allows a zero-fee transaction
to create a dust output provided it is spent within the same package, enabling
anchor outputs without permanently bloating the UTXO set.

`packages.{h,cpp}`:: **New** — package validation rules; what constitutes a valid
package and how ancestor sets are checked.

`rbf.{h,cpp}`:: Replacement rules, now working with feerate diagrams from `TxGraph`.

`fees/`:: **New subdirectory** — `CBlockPolicyEstimator` moved here from
`policy/fees.{h,cpp}`, and it is now itself a `CValidationInterface` subscriber
rather than being called directly from the mempool. `estimateSmartFee` remains the
entry point used by the wallet and by RPC.

`feerate.{h,cpp}`:: `CFeeRate`, satoshis per kvB.

[[kernel]]
== `kernel/`

A region that did not exist in 2021. `libbitcoin_kernel` is the validation engine
extracted so it can be used without a node: no P2P, no RPC, no wallet.

What lives here is a good definition of "consensus-critical plus what it needs":
{repo}/src/kernel/chainparams.cpp[`chainparams`],
{repo}/src/kernel/cs_main.h[`cs_main`] itself,
{repo}/src/kernel/mempool_entry.h[`mempool_entry`], mempool options and limits,
`disconnected_transactions`, `coinstats`, `chain`, and the
{repo}/src/kernel/notifications_interface.h[`kernel::Notifications`] interface
through which the engine reports progress, warnings, and fatal errors to whatever is
embedding it.

The public surface is a C API in
{repo}/src/kernel/bitcoinkernel.h[`bitcoinkernel.h`] with a C++ RAII wrapper
alongside it. It is experimental and gated behind `BUILD_KERNEL_LIB`. The
demonstration consumer is {repo}/src/bitcoin-chainstate.cpp[`bitcoin-chainstate`].

Alone among the libraries, `libbitcoin_kernel` is intended to eventually have a
stable documented interface. The others are explicitly unstable.

[[node]]
== `node/`

Node-level glue: everything that is neither consensus-critical nor
network-protocol-specific, in the `node::` namespace. It has absorbed a great deal
of what used to be in `init.cpp` and `validation.cpp`.

Highlights beyond those already covered:

* `*_args.cpp` files — `chainstatemanager_args`, `mempool_args`, `blockmanager_args`,
  `peerman_args`, `database_args`, `mining_args`. Each translates `ArgsManager`
  settings into a typed options struct, so the subsystems themselves never read
  command-line arguments. This is the pattern that lets the kernel be configured
  programmatically.
* {repo}/src/node/kernel_notifications.h[`kernel_notifications`] — the node's
  implementation of the kernel notification interface.
* {repo}/src/node/warnings.h[`warnings`] — node warnings as a managed object rather
  than a global string.
* `eviction.cpp` — inbound peer eviction logic, extracted from `net`.
* `timeoffsets.cpp` — peer time offset tracking.
* `txreconciliation.cpp` — Erlay set reconciliation state.
* `interfaces.cpp` — the node-side implementations of the `interfaces/` classes.
* `mini_miner.cpp` — a lightweight block-template simulator used for fee bumping.

[[interfaces]]
== `interfaces/` and `ipc/`

The 2021 document framed this region around a good question — why should the wallet
not simply call the fee estimator directly? — and answered it with a proposal.
The answer is now load-bearing infrastructure.

The wallet does not hold a `NodeContext`. `CWallet` holds an
`interfaces::Chain* m_chain` and calls `wallet.chain().estimateSmartFee(...)`. The
implementation on the other side may be an in-process call or a Cap'n Proto message
across a socket, and the wallet cannot tell.

The interfaces:

* {repo}/src/interfaces/chain.h[`Chain`] — used by the wallet to read chain and
  mempool state and subscribe to notifications.
* `ChainClient` — used by the node to start and stop chain clients.
* {repo}/src/interfaces/node.h[`Node`] — used by the GUI to control the node.
* {repo}/src/interfaces/wallet.h[`Wallet`, `WalletLoader`] — used by the GUI and
  node to drive the wallet.
* {repo}/src/interfaces/mining.h#L107[`Mining`] — **new**; see below.
* {repo}/src/interfaces/init.h[`Init`] and {repo}/src/interfaces/ipc.h[`Ipc`] —
  process startup and IPC connection management.
* `Echo` — a trivial interface used to test the IPC plumbing end to end.

{tree}/src/ipc[`src/ipc/`] holds the Cap'n Proto schemas, the code generator, and
the vendored libmultiprocess subtree. `ENABLE_IPC` defaults to `ON` on non-Windows.
See {repo}/doc/design/multiprocess.md[`doc/design/multiprocess.md`] and
{repo}/src/interfaces/README.md[`src/interfaces/README.md`].

[[rpc]]
== `rpc/`

{repo}/src/rpc/server.h#L89[`CRPCTable`] is the dispatch table;
{repo}/src/rpc/server.h#L42[`CRPCCommand`] is one entry. Methods are declared with
`RPCHelpMan`, which serves triple duty: it generates the help text, validates and
converts arguments, and documents the result shape — so the help output cannot drift
from the implementation.

Files are grouped by subject: `blockchain.cpp`, `mempool.cpp`, `mining.cpp`,
`net.cpp`, `node.cpp`, `rawtransaction.cpp`, `output_script.cpp`, `signmessage.cpp`,
`txoutproof.cpp`, `fees.cpp`, `external_signer.cpp`. Wallet RPCs live separately
under `wallet/rpc/`, which is what allows them to be absent when the wallet is
compiled out. `client.cpp` is the `bitcoin-cli` side.

The HTTP transport underneath (`httpserver.cpp`, `httprpc.cpp`) is a separate
concern and is covered in the architecture document — note that it no longer uses
libevent.

[[qt]]
== `qt/`

Around 59 translation units implementing the Qt GUI. It talks to the node through
`interfaces::Node` and to wallets through `interfaces::Wallet`, never directly,
which is what allows `bitcoin-gui` to run as a separate process from `bitcoin-node`.

Project convention: new features are exposed on RPC first and only then in the GUI,
because the RPC test surface is far stronger than the GUI's.

[[wallet]]
== `wallet/`

Descriptor wallets on SQLite, and nothing else. `bdb.cpp` is gone; only
{repo}/src/wallet/migrate.h[`migrate.{h,cpp}`] remains, to read legacy Berkeley DB
files for one-way migration.

* `wallet.{h,cpp}` — `CWallet`, holding `interfaces::Chain* m_chain`.
* `scriptpubkeyman.{h,cpp}` — `DescriptorScriptPubKeyMan`, which derives and tops up
  script pubkeys from descriptors.
* `coinselection.{h,cpp}`, `spend.{h,cpp}` — the coin selection algorithms (branch
  and bound, knapsack, SRD) and transaction construction.
* `sqlite.{h,cpp}`, `walletdb.{h,cpp}` — storage.
* `feebumper.{h,cpp}` — RBF fee bumping.
* `external_signer_scriptpubkeyman.{h,cpp}` — hardware wallet support.
* `rpc/` — wallet RPC methods.
* `wallettool.{h,cpp}` — the `bitcoin-wallet` offline tool.

See {repo}/doc/managing-wallets.md[`doc/managing-wallets.md`] and
{repo}/doc/descriptors.md[`doc/descriptors.md`].

[[mining]]
== `node/miner.{h,cpp}` and `interfaces/mining.h`

{repo}/src/node/miner.h#L60[`BlockAssembler`] builds a block template from the
mempool. With cluster mempool in place it consumes a linearisation from
`TxGraph::BlockBuilder` rather than walking an ancestor-feerate index.

The larger change is that mining is now a first-class interface.
{repo}/src/interfaces/mining.h#L107[`interfaces::Mining`] exposes
{repo}/src/interfaces/mining.h#L146[`createNewBlock`], template updates, and
`waitTipChanged`, held as `NodeContext::mining`. This exists so that mining software
can be driven over IPC — a real client of the multiprocess work rather than a
hypothetical one — and so that `getblocktemplate`-style polling can be replaced by
notification.

[[common]]
== `common/` and `util/`

The bottom of the stack, split by level. `libbitcoin_util` is lower-level (threads,
sockets, strings, filesystem, time, logging, `SignalInterrupt`, `ThreadPool`);
`libbitcoin_common` is higher-level but still shared (`ArgsManager`, settings,
`bloom`, `signmessage`, `netif`, `pcp`, `run_command`).

The distinction is enforced by the dependency graph in
{repo}/doc/design/libraries.md[`libraries.md`] and is worth respecting: putting
something in `util/` that depends on `common/` will fail the build for
non-obvious-looking reasons.

Note also that the old catch-all `util/system.{h,cpp}` has been dismantled —
`ArgsManager` to `common/args.h`, thread helpers to `util/thread.h`, filesystem
helpers to `util/fs_helpers.h`, and so on. Any 2021-era reference to
`util/system.h` needs re-resolving.
